## 2026.11.13(금).md : Java 스프링 부트 복습

## 1. 스프링 부트(Spring Boot)

- 스프링(Spring) : Java로 웹사이트나 서버를 만들 때 필요한 기능들을 미리 모아둔 거대한 '종합 도구 상자(프레임워크)'다. 다만 예전 스프랑은 처음 시작할 때 해줘야 할 초기 설정이 너무 많고 복잡했다.

- 스프링(Spring Boot) : 기존 스프링의 복잡한 초기 설정을 자동으로 처리해 주는 간편 버전이다.

  - 웹 서버(내장 톰캣)가 이미 안에 들어있어서 따로 서버를 설치하고 연결할 필요 없이 바로 실행할 수 있다.
 
  - 덕분에 개발자는 번거로운 세팅 대신 실제로 만들고 싶은 기능(비지니스 로직)에만 집중할 수 있다.
 
## 2. 학습 환경 및 기술 스택 

수업에서 다른 `_boot2_db` 에제 프로젝트를 기준으로 정리한 구성 요소.

- **java 17 / Spring Boot 3.5.6(Gradle)** :  프로그램의 뼈대와 실행 환경

- **MariaDB** : 데이터를 실제로 저장하는 데이터베이스(창고)

- **MyBatis** : 자바 코드와 SQL(SQL 명령어)을 깔끔하게 연결해 주는 도구

- **JSP(JSTL + Tomcat Jasper)** : 사용자에게 보여줄 화면(HTML)을 만드는 뷰 도구

- **Lombok** : 반복되는 코드(Getter/Setter 등)를 어노테이션으로 줄여주는 도구

- **log4jdbc** : DB에 어떤 SQL이 실행됐는지 콘솔에 보기 쉽게 출력해 주는 도구

## 3. 한눈에 보는 웹 요청 흐름 (식당에 비유해서)

브라우저에서 `http://localhost:8080/list` 주소를 입력했을 때, 데이터가 움직이는 순서다.

1. 사용자 (손님) -> `/list` 화면 달라고 요청

2. Controller(`EmpController`) (웨이터) -> 주문을 받아서 매니저에게 전달 

3. Service(`EmpService`) (매니저) -> 필요한 작업(비지니스 로직)을 정리해 주방에 지시

4. DAO(`EmpDAO`) + MyBatis(`emp.xml`) (요리사) -> DB에 보낼 SQL문을 실행해서 재료(데이터)를 꺼내옴

5. MariaDB(냉장고 / 창고) -> 실제 사원 데이터가 들어있는 곳

6. DTO(`EmpDTO`) (쟁반) -> 꺼내온 사원 데이터를 담아서 계층 간에 안전하게 나르는 상자

7. View(`result.jsp`) (완성된 접시) -> Controller가 `Model`에 담아 건네준 데이터를 받아 화면으로 그려줌

## 4. 나중에 헷갈리기 쉬운 핵심 어노테이션 & 설정 정리 

- `@Controller` : "이 클래스는 웹 요청을 받는 창구다" 라고 스프링에게 알려주는 표식.

- `@Autowired` (의존성 주입, DI) : 개발자가 직접 `new EmpServiceImpl()` 하지 않아도, 스프링이 알아서 필요한 객체를 찾아 꽂아주는 기능.

- `Model` : Controller가 조회한 데이터를 JSP 화면으로 넘길 때 담아두는 '데이터 전달 상자'(`model.addAttribute`("이름", 데이터)).

- `@ResponseBody` : JSP 화면으로 이동하지 않고, 반환하는 글자나 데이터 자체를 브라우저에 그대로 띄울 때 사용(`/` 요청 시 `"hello"` 출력).

- View Resolver 설정 (`application.properties`)

  - `spring.mvc.view.prefix=/WEB-INF/jsp/`
 
  - `spring.mvc.view.suffix=.jsp`
 
  - 컨트롤러가 `"result"` 라고만 반환해서 스프링이 앞뒤를 붙여서 `/WEB-INF/jsp/result.jsp` 파일을 찾아줌.
 
- MyBatis 매퍼(`emp.xml`, `dynamic.xml`)

  - 자바 코드 안에 SQL문을 직접 쓰지 않고 XML 파일로 분리해 관리함
 
  - `emp.xml`은 기본 조회, `dynamic.xml`은 조건에 따라 쿼리가 달라지는 동적 쿼리용.

 ## 싱글톤 패턴(Singleton Pattern) 

 - 왜 쓸까? : 필요할 때마다 객체를 `new`로 새로 만들면 메모리가 낭비됨. 프로그램 전체에서 단 하나의 객체만 만듣어서 모두가 공유하기 위해 사용.

 - 스프링 부트와 무슨 상관? : 스프링이 `@Controller`, `@service` 같은 객체(빈, Bean)들을 관리할 때도 내부적으로 이 싱글톤 원리를 써서 하나만 만들어 재사용함.

전체 코드 정리 (`Singleton.java`)

``` java
   public class Singleton {
    // 1. 단 하나만 만들어 보관해 둘 공유 변수 (static)
    static Singleton instance = null;

    // 2. 외부에서 new Singleton()으로 막 만들지 못하게 잠금 (private)
    private Singleton() {}

    // 3. 객체를 받아가는 유일한 통로
    public static Singleton getInstance() {
        if (instance == null) { // 아직 없을 때만 딱 한 번 생성
            instance = new Singleton();
        }
        return instance; // 이미 있으면 기존 객체 그대로 반환
    }
}
```

> `SingleExam.java`에서 `GetInstance()`를 두 번 호출해 `s1`, `s2`에 담아도 결국 둘은 메모리상 완전히 같은 하나의 객체를 가르키게 된다.
