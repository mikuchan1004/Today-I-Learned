### 데이터베이스 (DB)
그냥 데이터를 아무렇게나 모아둔 게 아니라 '여러 사람이 공유하고 사용할 목적으로 통합해서 관리하는 데이터의 집합'.

* **통합된 데이터** : 똑같은 내용이 중복되는 걸 최대한 없앴다는 뜻

* **저장된 데이터** : 컴퓨터가 접근할 수 있는 저장매체에 안전하게 저장되어 있다.

* **운영 데이터** : 조직의 고유한 업무를 수행하는 데 없어서는 안 될 꼭 필요한 데이터.

* **공유 데이터** : 여러 응용 프로그램에서 사용자들이 동시에 같이 쓸 수 있어야 한다.

----

### 데이터베이스 시스템 

사용자가 데이터베이스를 쉽게 쓸 수 있도록 도와주는 전체적인 시스템을 말한다.

* **DBMS(데이터베이스 관리 시스템)** : 사용자와 DB 사이에서 데이터를 직접 관리해 주는 소프트웨어.

* **3단계 스키마 구조** : 외부 스키마(사용자 관점), 개념 스키마(조직 전체 관점), 내부 스키마(물리적 저장 관점)로 나눠서

데이터의 독립성과 안전성을 지켜준다.

----

### 관게형 데이터 모델 (Relational Data Model)

요즘 제일 많이 쓰는 방식. 데이터를 엑셀처럼 생긴 **2차원 테이블** 형태로 표현하는 것.

* **릴레이션(Relation)** : 데이터가 들어있는 하나의 테이블 그 자체

* **튜플(Turple)** : 테이블의 가로줄(행, Row)을 말한다. 즉, 데이터의 한 건, 한 건을 의미

* **속성(Attribute)** : 테이블의 세로줄(열, Column)이며, 데이터의 특징을 나타낸다.

* **기본키(PK) & 외래키(FK)** : 각 데이터를 확실하게 구별해주는 핵심 열쇠(PK)와, 다른 테이블과 연결해 주는 열쇠(FK)이다.

**설계할 때 헷갈리면 큰일이 나는 이유**

데이터베이스에서 기본키(Primary Key)는 각 데이터를 유일하게 구분해 주는 '주민등록번호' 같은 거고,

외래키는(Foreign Key)는 다른 테이블의 데이터를 찾아가기 위한 '주소지'나 '연결고리' 같은 것.

이 둘의 역할을 헷갈려서 설계를 망치면 다음과 같은 끔찍한 재앙이 일어난다.

1. 데이터의 정체성이 사라진다(개체 무결성 훼손)

기본키는 절대 중복되거나 비어있으면(NULL) 안 됀다. 그런데, 기본키로 써야 할 걸 외래키처럼 느슨하게 

관리해 버리면 똑같은 이름이나 정보를 가진 데이터가 여러 개 생겨버린다.

**결과** : 나중에 'A 회원 정보 좀 지워줘!'라고 명령했을 때, 데이터베이스는 어떤 A 회원인지 구별하지 못해서 

엉뚱한 사람을 지우거나 에러를 뱉어낼 것이다.

2. '고아 데이터'가 넘쳐난다. (참조 무결성 위배)

외래키는 두 테이블 간의 관계를 단단하게 묶어주는 역할을 한다. 

예를 들어 '주문' 테이블의 외래키는 '고객' 테이블의 기본키를 바라보고 있어야 한다.

**결과** : 이걸 헷갈려서 연결을 안 해두거나 반대로 해두면, 고객이 탈퇴해서 정보를 싹 지웠는데도 

주문 내역에는 주인을 잃어버린 '고아 데이터(Orphan Data)'가 덩그러니 남게 됀다. 

데이터베이스에 쓰레기가 쌓이는거나 다름없다.

3. 엉뚱한 정보가 합쳐진다. (조인(JOIN) 오류)

관계형 데이터베이스의 핵심은 여러 테이블을 엮어서(JOIN) 의미 있는 정보를 뽑아내는 것이다.

이때 서로 아귀가 맞는 기본키와 외래키를 기준으로 테이블을 합쳐야 한다.

**결과** : 키를 헷갈려서 아무 열이나 기준으로 테이블을 합쳐버리면?

'홍길동' 회원의 구매 내역에 엉뚱하게 '아무개' 회원의 장바구니 리스트가 섞여서 나오게 된다.

회사에서 이런 통계를 냈다가는 바로 해고감!

4. 시스템이 뻗어버릴지도 모른다(성능 저하)

보통 데이터베이스 관리 시스템(DBMS)은 기본키와 외래키를 기준으로 데이터를 엄청나게 빨리 찾을 수 있게 내부적으로 

'인덱스(index)'라는 색인을 만든다.

**결과** : 열쇠의 역할을 헷갈려서 엉터리로 구조를 짜면, 컴퓨터가 방대한 데이터 속에서 길을 잃고 해메느라 

검색 속도가 바닥을 치게 됀다.

한마디로, 기본키와 외래키를 헷갈리면 "데이터는 쓰레기가 되고, 검색은 느려지며, 시스템은 망가진다"는 소리.

그러니까 처음 테이블 뼈대를 잡을 때 똑바로 하자.

### 관계 대수 

원하는 데이터를 찾기 위해 **'어떻게(How)'** 검색해야 하는지 수학적으로 깐깐하게 표현한 절차적 언어.

* **순수 관계 연산자** : 셀렉트(조건에 맞는 행 찾기), 프로젝트(원하는 열만 빼오기), 조인(두 테이블 합치기) 등

* **일반 집합 연산자** : 합집합, 교집합, 차집합, 카티션 프로덕트

----

### SQL (Structured Query Language) 기초 

복잡한 관계 대수를 바탕으로, 사람이 실제로 DB에 명령을 내릴 때 쓰는 표준 언어.

'무엇(What)'을 원하는지만 말하면 DBMS가 알아서 해주는 똑똑한 비절차적 언어.

* **DDL(데이터 정의어)** : 테이블이라는 뼈대를 만들고 고치고 지운다.(`CREATE`, `ALTER`, `DROP`)

* **DML(데이터 조작어)** : 테이블 안의 실제 데이터를 넣고, 빼고, 수정한다.

실무에서 제일 많이 쓰고 쿼리 짜다 제일 많이 틀리는 부분이니까 주의! (`SELECT`, `INSERT`, `UPDATE`, `DELETE`)

* **DCL(데이터 제어어)** : 누가 데이터를 볼 수 있는지 접근 권한을 관리 (`GRANT`, `REVOKE`)
